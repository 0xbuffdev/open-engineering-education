# REL-I02 — Deterministic curriculum archive and trusted installation

**Status:** implementation candidate under [accepted RFC 0005](../rfcs/0005-immutable-curriculum-releases.md)
and [Stage 2 tracker #257](https://github.com/0xbuffdev/open-engineering-education/issues/257).
**Not authorized for GitHub Release, PyPI publication, OEE readiness promotion,
learner assessment or Workspace/Content/0xNAND production cutover.**

## Source of truth and artifact identities

- **Academic authority:** OEE `curriculum/**/*.md`, related public specs and
  catalogues, and licensed source references. There is ONE Toolkit parser.
- **Release manifest authority:** REL-I01
  [release_manifest.py](oee_toolkit/release_manifest.py). Build only from one
  explicit reviewed Git commit; fail if any current course, public linked
  assessment, catalog, required license or source digest is missing.
- **Archive:** REL-I02
  [release_archive.py](oee_toolkit/release_archive.py) builds an **uncompressed,
  canonical USTAR**. It contains `release.json` plus exactly the files
  listed in that manifest. Every file has a complete digest and size.
- **Human-facing release ID:** illustrative `YYYY.MM.N`, independent of the
  OEE v0.2.0 specification, Toolkit package release version and future
  course-export format. It is never a moving pointer or an authentication claim.
- **Verified identity:** full SHA-256 of the exact UTF-8 `release.json`,
  **not** only the release ID, tag, GitHub asset URL or a text string `latest`.
  Consumers will carry this value in a separately approved release lock.

A full Git commit SHA remains inside the verified manifest for publisher audit,
but **not** in the target learner/author consumer interface. REL-I03 will
implement the installed release resolver and exportVersion 2.

## Deterministic archive format

The archive is canonical, byte-for-byte reproducible on Linux, macOS and
Windows: fixed USTAR mode/uid/gid/mtime, no PAX records, no compression,
only normalized regular-file paths in UTF-8 byte sort order, and no hidden
entries. `release.json` is included but does not hash itself. An independent
reader rejects archive padding/trailing changes, duplicates, missing/extra
files, symlinks and hard links, absolute/parent-traversal paths, invalid
file sizes and any discrepancy from a canonical reserialization.

Each source file's **original committed bytes** are hashed and stored,
never the CRLF-normalized working-tree copy. The archive has bounded
per-file, total and manifest sizes to avoid unsafe unbounded extraction.

REL-I02 uses deterministic **serialization**, not a second course grammar.

## Detached signature and trusted key

The proposed local proof mechanism is **Ed25519** over a canonical
`attestationVersion: 1` JSON record containing the release ID, full manifest
SHA-256 and full TAR SHA-256. It is detached from the archive.

- A maintainer uses a separately managed private signing key; **no private
  key is generated by the release CLI, committed to OEE or uploaded to CI
  artifacts**.
- Verification requires the manifest digest and an **independently trusted
  steward public key supplied explicitly**. It does not accept a self-declared
  public key embedded in the downloaded archive.
- SHA-256 alone detects unexpected changes; the verified signature proves
  possession of the corresponding key, **not** that the steward was authorized
  or that a public release was approved. Approval, trust/key rotation and
  revocation must be recorded and reviewed separately.
- Signing is an **explicit human-gated operation**. A signature is not
  package publication or OEE academic conformance.
- Signing and verification require the optional Python dependency
  `cryptography`, available when installing the Toolkit as
  `oee-toolkit[release]` from a future approved distribution. The default
  core parser remains dependency-free.

Before a real release, the steward must separately approve the trusted
public key distribution, signed provenance/attestation policy, rights and
notice audit, archived source hash, and GitHub Release upload. This candidate
PR grants **none** of these approvals.

## Local disposable candidate example

The source SHA is **publisher-only**. These commands create local candidate
files, not published releases. No implicit network access:

```sh
python3 -m pip install "cryptography>=44,<50"

# From an OEE repository; use a real reviewed commit for production proposals.
REVISION="$(git rev-parse HEAD)"
python3 scripts/build-curriculum-release-archive.py build \
  --repo . --revision "$REVISION" --release-id 2099.01.1 \
  --output candidate.tar

# Obtain the manifest SHA-256 from the completed REL-I01 candidate
# verification result, independently review it, then set:
MANIFEST_SHA256="<approved-full-64-character-manifest-digest>"

# Signing keys are maintained OUTSIDE the repo; never paste a secret here.
python3 scripts/build-curriculum-release-archive.py sign \
  --archive candidate.tar --expected-manifest-sha256 "$MANIFEST_SHA256" \
  --private-key /secure/steward-ed25519-private.pem \
  --attestation candidate.attestation.json --signature candidate.sig

python3 scripts/build-curriculum-release-archive.py verify \
  --archive candidate.tar --expected-manifest-sha256 "$MANIFEST_SHA256" \
  --attestation candidate.attestation.json --signature candidate.sig \
  --trusted-public-key /trusted/steward-ed25519-public.pem

# Explicit existing, trusted local store; no network and no-clobber.
mkdir -p candidate-store
python3 scripts/build-curriculum-release-archive.py install \
  --archive candidate.tar --expected-manifest-sha256 "$MANIFEST_SHA256" \
  --attestation candidate.attestation.json --signature candidate.sig \
  --trusted-public-key /trusted/steward-ed25519-public.pem \
  --store candidate-store
```

**For actual approval**, obtain the expected manifest SHA independently;
never derive it solely from an untrusted download and call that an
authenticated source. The command uses exclusive, no-clobber creation for
candidate and detached-signature output files. Signing and installing cannot
overwrite existing artifacts, and installing an already occupied release ID
under a different manifest digest is rejected.

## Offline install boundaries

The store must be an existing, caller-owned trusted directory and must not
be a symlink. The installer checks the *entire* archive against the pinned
manifest digest and detached signature **before writing anything**. It
creates one temporary staging directory, populates verified source files
without following archive entry paths outside staging, and atomically
promotes it to `<store>/<manifestSha256>`, protected by an exclusive
cooperative-installer lock. It does not write the consumer's lockfile,
learner files, R2, private databases or a moving `latest` alias.

The store's access control is part of the trust boundary. Local untrusted
processes must not have write access to the store; a cooperative lock does
not substitute for filesystem permissions. Installer behavior for revoked
signers or an untrusted publisher still depends on a separately reviewed
trust/attestation policy.

## Tests and remaining gates

The new [archive test suite](../tests/test_curriculum_release_archive.py)
covers identical full committed bytes, invalid signatures/keys/digests,
modified claims/archives, duplicate/extra entries, traversal, absolute
paths, symlinks, modified TAR metadata, release ID collision, existing
store corruption and repeated-install refusal.

The [REL-I02 CI workflow](../.github/workflows/curriculum-release-archive.yml)
builds a **test-only complete 76-course candidate**, verifies it with an
ephemeral non-release Ed25519 key, installs it offline, then compares
candidate TAR bytes across Linux, Windows and macOS. Ephemeral private keys
are removed before artifact upload. This CI does not publish or certify
any academic content.
