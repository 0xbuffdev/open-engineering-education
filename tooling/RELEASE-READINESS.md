# OEE Toolkit release-readiness verification

**Milestone:** OT-I05 — independent execution, provenance, licensing and
distribution decision.

**Status:** Candidate for public steward review. This document records
**release-readiness evidence**, not an official Toolkit package, CLI
installation, stabilized Python API or new release tag.

The [accepted RFC 0002](../rfcs/0002-toolkit-stewardship-and-licensing.md)
approves source stewardship and file-scoped licensing. It does **not**
automatically authorize a packaged Toolkit release. The canonical
[OEE specification](../spec/README.md) and educational Markdown retain
authority over any derived Toolkit export.

## One supported format, one parser

The **internal publisher/golden test CLI** is
`python -m tooling.oee_toolkit._publisher_cli`, using exact immutable
Git-source v0.2.0 data and historical export format 1 only for source
regression evidence. The **installed Toolkit consumer CLI** is
`oee-toolkit` and exports **only version 2** from a separately verified
and digest-locked curriculum release. The source commit remains internal
provenance, not a consumer input. See
[REL-I03](RELEASE-CONSUMER.md) for the new active consumer contract.
Python 3.11+ and the standard library suffice for offline export; the
optional release-signing helper uses an approved cryptography dependency.

The implementation uses the existing shared
[course checker](../scripts/check-outcome-curriculum.py), rather than a
second Markdown parser. It accepts only a full immutable lowercase
40-character source commit SHA; it neither downloads the curriculum
nor substitutes moving HEAD, a branch name or a dirty worktree for a
selected revision.

A `passed` result means **the structural checks performed passed**.
It cannot authenticate educational assessment quality, award learner
mastery, make a curriculum `tested`/`verified`, establish accreditation,
or approve official OEE conformance. Unsupported formats and incomplete
checks never count as successful coverage.

No parser or converter is supplied for earlier OEE formats. Older
course samples and resource-map v1 inputs appear only as **rejection
fixtures**, not as supported runtime behavior. No backward
compatibility or migration adapters are authorized by OT-I05.

## Independent, clean-checkout smoke

The [release smoke](../tooling/interop/verify_release_readiness.py)
creates a **new temporary local Git clone** from an existing trusted
OEE checkout, then invokes the internal publisher-only inspection/test CLI in that
independent checkout. No Python package install, account, paid
resource, private repository, model API or network service is needed
once the public Git checkout is available.

From a clean local public OEE checkout:

```sh
python tooling/interop/verify_release_readiness.py \
  --source . --report ../toolkit-readiness.json
```

The script checks:

- Whole-repository OEE v0.2.0 structural validation with no skipped
  required checks and `manualReviewRequired: true`.
- Direct pinned exports of SEF1, SEF10, APP1 and APP17, repeated with
  **byte-identical UTF-8/LF JSON**, source commit and format identity.
- Exact-commit golden fixtures in
  [the interop manifest](../tooling/interop/fixtures/pins.json), which
  remain immutable and are never regenerated by the smoke.
- Explicit rejection of OEE v0.1.0 and missing source objects, rather
  than continuing with HEAD or permitting a previously supported
  parser.
- Existing-file preservation when export input is invalid, along
  with successful atomic JSON file creation for valid input.
- Identical pinned exports after moving **only the disposable clone's**
  HEAD with an empty local Git commit.
- Presence of both licenses, notice, accepted RFC, author/citation
  records, DCO and the Toolkit file-scope licensing explanation.

The script writes a deterministic field-structured JSON report to the
requested `--report` destination. It does not save a learner record,
publish a package, create a tag or modify the original checkout.
The smoke's disposable Git commit hash will differ between runs;
pinned-export bytes and golden digests must stay identical.

[Toolkit release CI](../.github/workflows/toolkit-release-readiness.yml)
runs this smoke on **Ubuntu, macOS and Windows** using the exact PR
checkout, full source history and `persist-credentials: false`,
preserving separate JSON evidence artifacts for each platform. The
workflow neither fetches sources while testing the CLI nor publishes
a GitHub release.

**Important:** OT-20's independent, installable **package artifact**

relabelled as a packaged-install test or official distribution.
Human legal/source-provenance review and any external distribution
approval also remain outstanding.

## Proposed packaged distribution candidate (Stage 1)

A source-buildable, **unpublished** Python distribution now lives in the
repository's `pyproject.toml` and `MANIFEST.in`. The actual course parser
and version classifier have one owner inside `tooling/oee_toolkit/`; the
repository checker invokes them rather than maintaining another
implementation. The installable CLI is `oee-toolkit`, with no required
third-party Python runtime dependencies.

[`toolkit-package.yml`](../.github/workflows/toolkit-package.yml) builds
wheel and source archives on Linux, macOS and Windows and invokes
[`verify_package_install.py`](interop/verify_package_install.py) from a
fresh isolated virtual environment outside the OEE source tree. That test
checks that the wheel works without repository maintenance scripts, produces byte-identical digest-locked **v2 JSON** from a locally installed
signed test release, includes MIT/NOTICE, excludes CC BY curricula and v1
golden exports, and refuses absent locks or Git consumer flags.
The source archive must independently rebuild into a wheel.

These are **new OT-20 technical acceptance tests**, not proof that the
artifact has been successfully tested until the CI run passes. The original
manual copyright, third-party rights, release-number selection, maintainer
smoke and explicit publication authorization below remain mandatory.
No PyPI publishing, GitHub Release or tag workflow has been added.

Until a distinct approved curriculum-release manifest is adopted, the
installed CLI still selects an exact source Git commit. The proposed next
stage would replace this consumer-facing requirement with an immutable,
digest-checked release ID while retaining reproducible source provenance.

## Cross-repository provenance and SSOT

The immutable [golden fixtures](../tooling/interop/golden/) are
derived from an earlier, explicitly recorded source commit in
[`pins.json`](../tooling/interop/fixtures/pins.json). They stay
unchanged as regression evidence even when the current OEE curriculum
or Workspace map pin advances.

The [interop CI](../.github/workflows/toolkit-interop.yml) selects one
reviewed **full Workspace commit** from that same manifest. It then
confirms that this current public consumer:

- accepts each historical golden export for its **recorded OEE source
  revision** and rejects a deliberately wrong revision;
- rejects the historical resource-map v1 **negative fixture**;
- rejects a **current Workspace v2 map** when paired with an export
  from a **different OEE commit**; and
- accepts that reviewed v2 map when paired with a fresh Toolkit
  export from **the map's own exact recorded source revision**.

The OEE-side advisory drift check may report a source mismatch
between the historical golden and today's reviewed map. This is an
expected provenance distinction, **not an error and not permission
to migrate resource mappings**. The Workspace's own independent
[release-readiness verification](https://github.com/0xbuffdev/oee-workspace/blob/main/docs/RELEASE-READINESS.md)
is a separate source-controlled gate.

No private Content repository, paid resource, 0xNAND enrollment or
parallel OEE Markdown parser is a dependency. This keeps the
specification, software implementation, derived exports and
learner-owned records in their respective single sources of truth.

## License, attribution and maintainer approval

The [file-level Toolkit license](LICENSING.md), [NOTICE](../NOTICE),
[MIT license](../LICENSE-MIT) and [CC BY 4.0 license](../LICENSE)
must be examined together. Original Toolkit software and
software-only interface schemas are MIT-covered to the extent of
contributors' rights. Normative course content and substantial
educational excerpts in golden exports are CC BY 4.0 derivatives.
A source-derived export must preserve attribution and the full
source revision. Contributor rights and third-party provenance
are **not** established merely by checking filenames. The OEE/0xBUFF
marks have separate trademark rules.

Before **any official Toolkit release or package**, the OEE steward
must independently approve:

- [ ] The signed OT-I05 PR, exact release-candidate SHA, and public
  release notes describing only existing implemented behavior.
- [ ] Green independent smoke reports on **Linux/macOS/Windows** at
  that exact signed head, plus existing source/export, golden/consumer
  integration, current-format rejection, quality and DCO checks.
- [ ] A clean local maintainer machine run, independent of GitHub CI.
- [ ] Real contributor copyright/licensing provenance, MIT and CC BY
  notice scope, attribution for educational export material,
  distribution rights and any third-party dependency notices.
- [ ] Approved support matrix, public import/API stability promise
  (currently **not approved**) and exact packaging mechanism if one
  is wanted.
- [ ] Toolkit software release number and artifact name, chosen by the
  steward. OEE **v0.2.0 is the specification version**, **not** an
  implied Toolkit package version.
- [ ] A separately explicit decision to tag, upload, distribute or
  announce any official artifact. This PR makes **none** of those
  decisions for the steward.

A clean test report is engineering evidence, not curriculum
accreditation or an endorsement of a particular student's work.
The source-only CLI remains available without an installed package.
